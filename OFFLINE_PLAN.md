# Офлайн-режим десктопной кассы — план

**Дата:** 2026-09-04 · **Статус:** предложение, код ещё не менялся.
**Область:** `desktop/` (Electron 28 + electron-vite + React 18, JSX) плюс минимальные
правки бэкенда для идемпотентности POS.

Все ссылки на файлы проверены по коду.

---

## 1. Что уже работает без интернета

| Механизм | Где | Покрытие |
|---|---|---|
| Кэш GET-запросов в `localStorage` | `desktop/src/shared/api.js:43` (`cached()`) | заказы, заказы кухни, товары, категории, залы — 5 чтений |
| Очередь записи (FIFO в `localStorage`) | `api.js:57-107` (`writeQueued`, `flushQueue`) | только статусы: `orders.updateStatus`, `kitchen.item*`, `kitchen.orderReady` |
| Флаг связи `isOnline` | `desktop/src/App.jsx:62,71-84` | из статуса kitchen-WS; индикатор и счётчик `↻ N` в `BottomBar` |
| Локальный HTTP-прокси + WS на порту 8765 | `desktop/electron/main.js:33-105` | мобильные клиенты в той же сети ходят через терминал |
| Прямая печать по TCP:9100 | `desktop/electron/main.js:120` (`printRaw`) | принтер доступен без интернета |
| Инбокс `OfflineJob` с идемпотентностью | `backend/app/modules/organizations/` | **обработчика нет** — grep по бэкенду пустой, задачи навсегда `pending` |

## 2. Что ломается

1. **Заказ создать нельзя.** `orders.create`, `addItem`, `removeItem`, `moveItem`, оплата,
   смены, приход/расход — обычные `api.post` без очереди. Офлайн `createOrder`
   (`desktop/src/modes/cashier/CashierMode.jsx:275-313`) падает в `catch` → тост
   «ошибка создания заказа» → корзина потеряна. Касса останавливается.
2. **Печать невозможна.** ESC/POS генерирует бэкенд и присылает по WS событием
   `print_job` (`CashierMode.jsx:105-115`); терминал только реле байтов в TCP.
3. **Вход невозможен.** PIN-вход — серверный `POST /auth/pin-login` (`api.js:187`).
   Перезагрузка терминала или смена смены во время аварии = сотрудник не зайдёт.
4. **Очередь теряет данные молча.** `saveQueue` глотает ошибку квоты
   (`catch { /* quota */ }`) → при переполнении `localStorage` (~5 МБ на кэш меню +
   заказов + очередь) запись исчезает без следа. В `flushQueue` при серверной ошибке
   элемент выбрасывается (`q.shift()`) без dead-letter.
5. **Расхождение сумм.** Клиент считает итог по кэшированному меню, сервер при создании
   пересчитывает по своей цене (`backend/app/modules/pos/service.py:150`). Цена изменилась
   за время офлайна → напечатанный чек ≠ синхронизированный заказ.
6. **Нумерация только серверная.** `_generate_daily_number` (`pos/service.py:734`) выдаёт
   `YYMMDD-NNN` со счётчиком на всю компанию. Офлайн номера нет вовсе; два терминала
   после синка дадут неверный порядок.
7. **Идемпотентности у POS нет.** `Idempotency-Key` поддержан только в финансах
   (`backend/app/modules/finance/router.py:183,197`). Реплей очереди после мутного
   таймаута = дубли заказов.

## 3. Принцип: local-first вместо online-first

Сейчас архитектура «пробуем сеть → при ошибке выкручиваемся». Для кассы это неверно.
Нужно: касса **всегда** пишет в локальную БД и рисует UI из неё, синхронизация — фоновый
процесс, о котором кассир знает только по счётчику. Тогда «интернет пропал» перестаёт
быть событием для пользователя.

---

## 4. Уровень 0 — не терять деньги

- **SQLite в main-процессе вместо `localStorage`** (`better-sqlite3`, доступ через IPC).
  Нет квоты 5 МБ, есть транзакции и WAL, файл выживает при очистке кэша Chromium,
  поддаётся бэкапу. `localStorage` для денег недопустим: одна тихая ошибка квоты =
  потерянная выручка.
- **Outbox-таблица** вместо JSON-массива:
  `id, seq, method, url, body, idempotency_key, depends_on, attempts, last_error,
  state (pending|sent|failed|dead), created_at`.
  Ничего не удаляем — только помечаем. `dead` видно в UI, можно переотправить руками.
- **`depends_on`** решает порядок: статус заказа не уходит, пока не подтверждён сам заказ.
  Сейчас такой связи нет — после дропа «отравленного» заказа его статусы летят в пустоту.
- **Идемпотентность POS:** клиент генерирует `client_id` (UUIDv4) при создании заказа,
  шлёт его в теле + `Idempotency-Key` в заголовке. На бэкенде — `Order.client_id`
  с уникальным индексом в рамках компании + миграция; повторный POST возвращает
  существующий заказ. Без этого реплей очереди включать нельзя вообще.
- **Цена фиксируется на клиенте:** передавать `unit_price` из снимка меню; при наличии
  `client_id` + офлайн-метки сервер доверяет ему и логирует расхождение в аудит.

## 5. Уровень 1 — продолжать продавать

- **Полный офлайн-цикл заказа** через outbox: создание, дозаказ, удаление позиции,
  пречек, оплата наличными, закрытие стола. Онлайн-подтверждение не нужно ни для одной
  из этих операций.
- **Локальная нумерация с префиксом терминала:** `YYMMDD-T1-007` (у `Order` уже есть
  `terminal_id`). Сервер при синке сохраняет локальный номер как `local_number`
  и присваивает свой сквозной. Иначе два офлайн-терминала выдадут одинаковые «005».
- **Генерация ESC/POS на терминале.** Самое ценное после outbox. Шаблон чека кэшировать
  (реквизиты, логотип, состав, порядок строк), собирать байты в рендерере, печатать через
  существующий `window.electron.print`. Серверная генерация остаётся основным путём
  онлайн; локальная включается при `isOnline === false`.
- **Офлайн-вход по PIN.** Кэшировать список сотрудников филиала и **только bcrypt-хэш**
  PIN (никогда plaintext; `pin_code`/`nfc_id` нигде не отображать), TTL 7–14 дней,
  обязательное обновление при каждом успешном подключении. Проверка локально по хэшу,
  сессия с пометкой `offline_login`, которую сервер валидирует при первом контакте.
  `permissions` берутся из того же кэша — они там уже есть.
- **Честный индикатор.** `isOnline` сейчас = состояние kitchen-WS и только после полного
  входа; WS может висеть «подключённым», пока REST уже недоступен. Нужен health-пинг
  лёгкого эндпоинта раз в 10–15 с и три состояния вместо двух:
  `онлайн` / `нет сети, N в очереди` / `синхронизация N…`.
- **Экран «несинхронизированное»** с dead-letter и кнопкой повтора.

## 6. Уровень 2 — не рассыпаться в зале

Делать только если устройств больше одного.

- **Мастер-терминал.** Прокси в `electron/main.js` уже принимает REST от планшетов
  и отдаёт 502, когда облако недоступно. Добавить локальный режим: держать состояние
  заказов смены в своей SQLite, отвечать планшетам самому, в облако сливать одним
  outbox'ом. Тогда официанты продолжают работать, а не только касса.
- **Кухня.** Статусы уже в очереди, но при обрыве повар не увидит новые позиции с кассы.
  Через локальный WS мастер-терминала — увидит.

## 8. Правила разрешения конфликтов

| Ситуация | Правило |
|---|---|
| Два терминала офлайн открыли один стол | Оба заказа принимаются, второй помечается «требует внимания», кассир объединяет вручную. Автомерж денег запрещён. |
| Дневной лимит блюда (`daily_limit`) | Офлайн по компании не проверяется → допускаем перепродажу и логируем. Делить лимит между терминалами — сложно и не окупается. |
| Цена изменилась во время офлайна | Действует цена на момент продажи (снимок), расхождение — в аудит. |
| Заказ отменён на сервере, пока терминал офлайн | Локальные изменения по нему → `dead`, кассир получает уведомление. |
| Реплей после мутного таймаута | Решается `client_id`, дубль невозможен. |

## 9. Фискализация (ОФД)

Фискальный чек создаётся на сервере (`backend/app/modules/fiscal/service.py:21`) со
статусом `pending|sent|failed`, ретраи ОФД живут там же — это верно. Но офлайн-продажа
остаётся нефискализированной до синка.

Предельный срок буферизации офлайн-чеков у ОФД в УЗ **надо подтвердить у оператора
(ЦОТУ / soliq.uz) или в договоре** — точную величину не выдумываем.

Для десктопа: хранить возраст самой старой несинхронизированной продажи, предупреждать
кассира при приближении к лимиту, не давать «уйти в офлайн навсегда» — при буфере старше
N часов показывать баннер.

---

## 10. Порядок работ

1. SQLite + outbox + идемпотентность POS (`client_id`, миграция) — фундамент.
2. Полный офлайн-цикл заказа и оплаты через outbox + локальная нумерация.
3. Генерация ESC/POS на терминале.
4. Офлайн-вход по PIN (кэш хэшей + TTL).
5. Health-пинг, три состояния индикатора, экран несинхронизированного + dead-letter.
6. Мастер-терминал для планшетов — по потребности.

Пункты 1–3 закрывают «кафе работает без интернета». 4–5 — «работает после перезагрузки
и кассир понимает, что происходит». 6 — только для нескольких устройств.

## Памятка при реализации

- Только JSX, никогда TypeScript. Комментарии по-русски, идентификаторы по-английски.
- CSS: только токены, без hex; `--color-interactive` только для ссылок.
- Имена классов в JSX — источник истины: недостающее добавляем в CSS, JSX не переименовываем.
- Гейты перед коммитом: `npm run check:css`, затем `npm run build`
  (3 известных предсуществующих нарушителя в `check:css` — норма).
- `git push` — только по явной просьбе.
