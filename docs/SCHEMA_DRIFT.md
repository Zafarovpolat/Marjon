# Расхождение схемы и моделей

## Что это

`alembic check` на чистом Postgres сравнивает модели SQLAlchemy с фактической
схемой, которую строят миграции. Первый честный прогон (задача `migrations` в
`smoke.yml`) показал **271 расхождение в 50 таблицах**.

До этого миграции в CI не запускались вообще: схему поднимал `create_tables.py`
из моделей, поэтому несоответствие никак не проявлялось.

## Откуда взялось

Миграции писали руками и забывали `nullable=False`. Пример:

```python
# модель: Mapped[bool] без Optional  ->  NOT NULL
is_superadmin: Mapped[bool] = mapped_column(Boolean, default=False)

# миграция: флага нет  ->  колонка допускает NULL
sa.Column("is_superadmin", sa.Boolean, server_default=sa.text("false"))
```

Какая схема окажется в бою, зависит от пути развёртывания. `docker-entrypoint.sh`
сначала пробует `alembic upgrade head` (тогда колонки **nullable**), и только
если миграции не применились — создаёт схему из моделей (**NOT NULL**).
На Render/Neon отрабатывает первый путь, то есть расхождение реальное.

## Что уже исправлено

| | |
|---|---|
| `ix_orders_status`, `ix_orders_table_number`, `ix_orders_branch_created` | объявлены в `Order.__table_args__` |
| `ix_attendance_logs_shift_id` | создан миграцией `p3q4sync03` |
| `users.avatar_url` VARCHAR(500) → String(512) | та же миграция |

Первый пункт — не косметика, а закрытая ловушка. Индексы создавались миграцией
`e9f0idx01`, но в модели не объявлялись. Модель для `autogenerate` — источник
правды, поэтому alembic считал их **лишними** и предлагал **удалить**. Один
неосторожный `alembic revision --autogenerate` оставил бы заказы без индексов
по статусу, столу и паре (филиал, дата) — без самых частых запросов дашборда
и кассы.

Осталось **266** расхождений, все типа `NOT NULL`.

## Почему 266 не тронуты

Вреда сейчас нет: приложение всегда пишет значения само, SQLAlchemy проставляет
`default=`. База просто не подстраховывает.

А вот исправление рискованное. `ALTER ... SET NOT NULL` падает на первой же
строке с `NULL` и оставляет миграцию применённой наполовину. Из 266 колонок:

- у **105** есть значение по умолчанию — их можно заполнить;
- у **61** его нет вовсе: это внешние ключи (`company_id`, `employee_id`,
  `order_id`), заполнить их нечем в принципе — `NULL` там означает битую строку;
- остальные объявлены в базовых классах (`created_at`, `updated_at` и подобные).

Делать это перед тестом в заведении не стоит. Это работа для отдельного окна
с бэкапом.

## Как подготовиться

Перед тем как браться, выясните, есть ли вообще проблема на ваших данных:

```bash
cd backend
DATABASE_URL=postgresql+asyncpg://... python scripts/check_nulls.py
```

Скрипт **ничего не меняет** — только считает строки с `NULL` в колонках, которые
модели требуют обязательными.

- **Ноль** — миграцию можно готовить спокойно, падать ей не на чем.
- **Нашлись строки** — видно конкретные таблицы и колонки; сначала данные.

На чистой базе с демо-данными в CI скрипт проверяет 551 колонку и находит ноль.
Это же значит, что сиды заполняют всё как положено.

## Порядок работ, когда дойдут руки

1. `check_nulls.py` на боевой базе. Если нашлись `NULL` — разобраться с данными.
2. Сделать бэкап.
3. Сгенерировать миграцию (`alembic revision --autogenerate`), для колонок со
   значением по умолчанию добавить перед `alter_column` заполнение:
   `UPDATE t SET c = <default> WHERE c IS NULL`.
4. Прогнать на копии боевой базы, замерить время: `SET NOT NULL` сканирует
   таблицу целиком и на больших таблицах блокирует её.
5. После этого сделать шаг `alembic check` в CI **блокирующим** — тогда он
   начнёт ловить новые забытые миграции, ради чего и задумывался.
