# План: Филиал как аккаунт (branch-as-account) и передача блюд между филиалами

> Статус: **НЕ реализовано** (на момент 2026-10-18).  
> Ниже — аудит того, что уже есть, и пошаговый план доработки.

## Что уже есть сейчас

1. **Модель филиала** (`branches`) уже содержит `login` + `password_hash`.
2. **Десктоп-вход по филиалу** реализован: `POST /auth/branch-login` выдаёт токен
   синтетического «терминального пользователя» (`service user`), привязанного к
   филиалу. Это работает для кассы/официанта/кухни на моноблоке.
3. **Веб-вход** (`POST /auth/login`) — только для `owner`/`superadmin`;
   филиальный логин сюда не подходит.
4. **Меню / блюда / склад** — company-wide: у одной компании один каталог,
   `products` / `ingredients` / `stock_items` не имеют `branch_id`.
5. **Web-админка** (`adminka.marjon.tech`) — одна на компанию, без
   branch-scoping: владелец видит всё сразу.

## Чего не хватает

| # | Функция | Почему важно |
|---|---------|--------------|
| 1 | **Веб-вход по филиалу** — отдельная админка (или тот же домен, но с фильтром по филиалу) | Владелец сети хочет дать менеджеру филиала доступ только к своим заказам, столам, складу |
| 2 | **Branch-scoped данные** — заказы, столы, склад, сотрудники должны быть привязаны к филиалу | Иначе филиалы «видят» чужие заказы и могут списать чужой товар |
| 3 | **Передача блюд между филиалами** — UI + backend для перемещения готовой продукции | Сеть с несколькими точками: готовят в одном, продают в другом |
| 4 | **Branch-scoped меню** — возможность скрывать/показывать блюда и цены по филиалу | Разные точки = разные цены и ассортимент |

## Пошаговый план реализации

### Этап 1 — Backend: аутентификация филиала в вебе (1–2 дня)

- Добавить `POST /auth/branch-web-login`:
  - принимает `login` + `password` филиала;
  - проверяет bcrypt-хэш;
  - выдаёт `access_token` с `auth_scope="app"`, `branch_id=…`;
  - **НЕ** создаёт синтетического `User` (это legacy десктопа).
- В `UserResponse` / `CompanyUserResponse` добавить `branch_id` (уже есть).
- Middleware / dependency `require_branch_user`:
  - если токен содержит `branch_id` → проверяем, что запрашиваемый ресурс
    принадлежит этому филиалу (заказы, столы, склад, сотрудники).
  - если `branch_id` отсутствует → работаем как owner (видим всё).

### Этап 2 — Backend: branch-scoped данные (3–4 дня)

- **Заказы** (`orders`): добавить `branch_id` (nullable, default NULL для
  обратной совместимости). Фильтровать список/детали по `branch_id` из токена.
- **Столы** (`tables`, `halls`): привязать к `branch_id`.
- **Склад** (`stock_items`, `warehouses`): у `warehouses` уже может быть
  `branch_id`; убедиться, что branch-пользователь видит только свои склады.
- **Сотрудники** (`users`): уже есть `branch_id`; фильтровать список.
- **Отчёты** (Z-отчёт, заказы, блюда): фильтровать по `branch_id`.
- **Смены** (`shifts`): привязать к филиалу.

### Этап 3 — Backend: меню и цены по филиалу (2 дня)

- **Меню**: ввести `branch_product_prices` (override цены/наличия для
  конкретного филиала). Если записи нет — берём глобальную цену.
- **Скрытие блюд**: поле `is_available_per_branch` или использовать
  `branch_product_prices.is_active`.

### Этап 4 — Backend: передача блюд / товаров между филиалами (2 дня)

- Новый endpoint `POST /warehouse/branch-transfers`:
  - `from_branch_id`, `to_branch_id`, `items[]` (ingredient_id / product_id, qty);
  - списывает с остатка `from` (expense), приходит на остаток `to` (purchase);
  - создаёт пару документов: `TransferOut` + `TransferIn` (или reuse
    `TransferDocument` с направлением).
- Проверка прав: только owner или manager с правом `transfers`.

### Этап 5 — Frontend: login-форма для филиала (1 день)

- Отдельная страница `/branch-login` (или переключатель на текущей `/login`):
  - поле «Логин филиала» + «Пароль»;
  - после успеха сохраняем токен в `localStorage` как обычный `access_token`.

### Этап 6 — Frontend: branch-scoped UI (2–3 дня)

- В `AuthContext` / `useAuth` добавить `branch_id` из токена.
- Во всех запросах (axios interceptor) автоматически добавлять
  `?branch_id=…` или `X-Branch-Id` header.
- Скрыть/заблокировать разделы, которые branch-пользователю не доступны
  (настройки компании, управление филиалами, финансы компании).
- В заголовке показывать имя текущего филиала.

### Этап 7 — Frontend: передача между филиалами (1 день)

- Новый экран «Перемещения между филиалами» в разделе Склад:
  - выбор «Откуда» / «Куда» (только филиалы пользователя);
  - таблица позиций с количеством;
  - кнопка «Провести перемещение».

1. Согласовать приоритет: сначала этап 1+5 (вход филиала в веб), потом
   остальное. Без авторизации нет смысла делать scoped-фильтры.
2. Зафиксировать требование: «передача блюд» — это перемещение готовой
   продукции (заказов/блюд) или сырья между складами? (В плане выше
   реализовано как складское перемещение сырья/товаров.)
